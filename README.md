# OpenTonton

**公開サービス： [OpenTontonを開く](https://opentonton.altneuland.workers.dev/)**

**みんなの都合を、ひとつに。** メールアドレスを登録せずに使える、30分単位の日程調整サービス。

## 実装済み

- イベントごとのランダムURL、タイトル・説明、複数候補日、日付ごとの複数候補時間帯
- 0〜24時の横スクロールタイムライン、青色のオーナー候補、参加者の〇、人数集計
- 候補日／参加者のソート、30〜120分の連続時間を考慮したおすすめ候補
- イベント内で一意のニックネーム＋パスワード認証（メールアドレスの取得・保存なし）
- パスワードはブラウザーで個別ソルト付きPBKDF2-SHA256 600,000回。サーバーは別ソルトを加えたSHA256ダイジェストのみ保存。復旧コードはランダム128bit、SHA256ハッシュ保存
- HttpOnly Cookieによるセッション、同一Origin確認、試行回数制限、権限分離、更新競合検出
- 復旧コードでの再設定、認証情報変更、ログアウト、回答削除、イベント削除
- 受付終了／再開、開催日時の確定、CSV出力（数式インジェクション対策付き）
- 個人情報入力禁止・URL閲覧範囲・削除期限の表示、登録時の同意
- 候補日は保存期限内のみ。保存期限＝最終候補日の翌日0時（JST）と作成から30日後の早い方
- 期限後はAPIで利用を拒否。毎時のWorker scheduledハンドラーと書込時の清掃で期限切れデータを削除
- サンプル回答はブラウザー内の一時状態で、サーバーには送信・保存しない

## 構成

React / TypeScript / Vinext（Vite・Next互換） / Cloudflare Workers / D1（SQLite） / Drizzle migrations。

UIは日本語、日本時間固定。イベントはURLで共有し、イベントを越えた共通ユーザーアカウントは作らない。内部IDはランダム値。ソースコードと実データは分離する。D1、秘密情報、ローカル実行状態はGitへ保存しない。

## 開発

Node.js 24以上、pnpm 11.25.0を使用。

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

ローカルDB初期化（初回のみ）：

```sh
pnpm exec wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_yielding_scream.sql
pnpm dev
```

開発用と公開先のデータベースは別。再実行時には未適用のマイグレーションだけ適用する。

```sh
pnpm test:integration
```

結合テストはビルド済みWorkerと隔離した一時D1で実行する。実データに接続しない。作成・認証・権限・候補外拒否・更新競合・受付終了・復旧・期限と連鎖削除を確認する。

## Cloudflare無料プランへ公開する準備

このソースはSitesでの非公開確認と、自分のCloudflareアカウントでの独立運用に対応する。GitHub公開だけでは動的APIやD1は稼働しない。

1. CloudflareでWorkers Freeプランを選び、`opentonton`というD1データベースを作成する。
2. GitHubに`production` Environmentを作り、必要に応じて公開前の承認者を設定する。
3. Environment secretに`CLOUDFLARE_API_TOKEN`を登録する。Workersのデプロイと対象アカウントのD1操作に必要な範囲に限定する。
4. Environment variablesに`CLOUDFLARE_ACCOUNT_ID`と`CLOUDFLARE_D1_DATABASE_ID`を登録する。
5. 利用規約・プライバシーポリシー・運営者・問い合わせ窓口を整備する（現在の画面は初期確認用）。
6. GitHub Actionsの「Deploy to Cloudflare (manual)」を手動実行する。APIトークンをリポジトリ内のファイルに書かない。
7. 公開されたworkers.dev URLで認証・回答を確認し、CloudflareでCron Trigger `0 * * * *`が有効であることと実行結果を確認する。

デプロイ処理はテスト・ビルド後、生成設定を自分のD1に置換し、マイグレーション・Worker公開を実行する。独自ドメインなしで開始できる。公開先のアカウント設定と無料枠の上限は運営者が確認すること。認証のハッシュ強度を無料枠に合わせて下げない。無料枠の本番CPU計測で制限に達する場合は、公開前に構成を再検討する。

## 削除・プライバシー

- DBの外部キー連鎖削除でイベント・参加者・認証情報・セッションを削除する。
- 清掃は1回100イベントずつに制限し、大量失効時はリクエスト時の清掃も併用する。保有上限と清掃遅延を監視すること。
- Cloudflare D1 Freeの復旧用履歴には削除後最大7日残り得る。バックアップから復元するときは公開再開前に期限切れを除去する。
- サーバーのリクエスト本文・パスワード・コード・回答はログへ出力しない。Worker Observabilityは明示的に無効。基盤のセキュリティ処理まで停止することを意味しない。
- 外部アクセス解析、メール送信、外部フォントは使用しない。
- 端末の最近開いたイベント一覧はlocalStorageに最大12件（ID・タイトル・期限のみ）。期限切れは一覧から除外する。認証はCookieに格納し、パスワードや復旧コードはブラウザーへ永続保存しない。
- 現在の初期版では、作成後の候補日・候補時間の変更は未実装。タイトル・説明・受付状態と確定日時は変更できる。

## 認証処理とWorkersの制限

ブラウザーのWeb Cryptoで、パスワードごとのランダム128bitソルトを使いPBKDF2-SHA256を600,000回実行する。登録・参加・復旧では新しいソルトを発行し、ログイン・認証情報変更・削除の確認では `/credentials` から公開KDFパラメーターだけを取得する。パスワード原文は送信しない。送信される導出値はパスワード相当の秘密情報として扱い、HTTPS以外での利用、ログ出力、ブラウザーへの永続保存を禁止する。

サーバーは導出値に別のランダム128bitソルトと用途識別子を加えSHA256で再ハッシュする。DBには方式・反復回数・二つのソルト・再ハッシュ後の値を保存する。DB内の値をそのまま送ってもログインできず、パスワード推測には各パスワード固有の600,000回の計算が必要になる。Worker内ではPBKDF2を実行しない。サーバーが悪意あるクライアントの実際の反復回数を証明できる方式ではないため、公式画面での入力長検証に加え、サーバーは導出値の方式・長さ・形式を検証する。

旧形式の保存済みハッシュは削除せず、復旧コードによる再設定で新形式に移行する。旧画面からパスワード原文が送信された場合は、画面の再読み込みを案内する。結合テストではWorker内のPBKDF2を意図的に無効化し、ブラウザー用送信処理を通した作成・ログイン・変更・復旧・削除を確認する。

作成リクエストは同じIPから毎分10回まで、作成成功は毎時20件まで。内部エラーは成功件数を消費しない。IP原文は保存せず、時間窓ごとのハッシュ識別子だけを期限付きで保持する。
