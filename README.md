# OpenTonton

**公開サービス： [OpenTontonを開く](https://opentonton.altneuland.workers.dev/)**

**みんなの都合を、ひとつに。** メールアドレスを登録せずに使える、30分単位の日程調整サービス。

## 主な機能

- イベントごとのランダムURL、タイトル・説明、複数候補日、日付ごとの複数候補時間帯
- 0〜24時の横スクロールタイムライン、青色のオーナー候補、参加者の〇、人数集計
- 候補日／参加者のソート、30〜120分の連続時間を考慮したおすすめ候補
- イベント内で一意のニックネーム＋パスワード認証（メールアドレスの取得・保存なし）
- パスワードはブラウザーで個別ソルト付きPBKDF2-SHA256 600,000回。サーバーは別ソルトを加えたSHA256ダイジェストのみ保存。復旧コードは暗号学的乱数で生成し、SHA256ハッシュ保存
- HttpOnly Cookieによるセッション、同一Origin確認、試行回数制限、権限分離、更新競合検出
- 復旧コードでの再設定、認証情報変更、ログアウト、回答削除、イベント削除
- 受付終了／再開、開催日時の確定、CSV出力（数式インジェクション対策付き）
- 個人情報入力禁止・URL閲覧範囲・削除期限の表示、登録時の同意
- 候補日は保存期限内のみ。保存期限＝最終候補日の翌日0時（イベントのタイムゾーン）と作成から30日後の早い方
- 期限後はAPIで利用を拒否。毎時のWorker scheduledハンドラーと書込時の清掃で期限切れデータを削除
- サンプル回答はブラウザー内の一時状態で、サーバーには送信・保存しない

## 表示言語

ブラウザーの優先言語が日本語なら日本語、それ以外なら英語で表示する。右上の言語選択で切り替えられ、選択は端末のlocalStorage（`ot_language`）へ保存する。保存済みの選択をブラウザー言語より優先し、保存できない環境でもその画面内では切り替えられる。

画面、説明、利用条件、既知のAPIエラー、CSVの見出しを日英で表示する。利用者が入力したタイトル・説明・ニックネームと認証情報は翻訳しない。日時・曜日・保存期限は表示言語と選択した表示タイムゾーンに合わせる。イベントのタイムゾーンは作成時に指定し、初期値は日本時間（JST / Asia/Tokyo）。作成後は固定する。参加者はイベント時刻、自分の端末の地域、任意の地域で表示できる。サーバーの初期HTMLと共通OGPは日本語を基本とし、画面の言語はブラウザーで確定する。

## タイムゾーンと保存期限

作成時にIANAタイムゾーンを選ぶ。変更すると選択済み候補日を解除する。候補日はイベント側の「今日」から保存期限内に制限する。初期版は時計が切り替わる日（夏時間や標準時の変更、存在しない／重複する深夜0時）を候補日にできない。日付と48個の30分枠の対応が一意な日だけ受け付け、APIでも検証する。

新規イベントは日付ごとの開始UTC時刻とタイムゾーンを保存する。送信された開始UTC時刻は信用せずサーバーで計算する。既存イベントは追加マイグレーションの既定値 `Asia/Tokyo` で引き継ぎ、既存の回答・確定日時・保存期限を変更しない。期限は最終候補日の終了と作成から30日後の早い方であり、表示地域の切替では変わらない。

画面のグループ分けと回答キーはイベントの日付・枠のまま。現地表示では同じグループ内に前日／翌日が含まれる場合があり、日付・曜日・UTCオフセットを表示する。表示側の夏時間で同じ時刻が二度現れる場合も、UTCオフセットで区別する。タイムラインはイベントの1日分を横に並べるため、現地表示では横軸が現地の0〜24時になるとは限らない。「参加できません」はイベント日付グループ内の全候補を対象とする。

CSVはイベント時刻・表示時刻（どちらもISO形式のUTCオフセット付き）、それぞれのタイムゾーン、UTC時刻を併記する。共有OGPはイベント情報を含めず、全ページ共通の日本語／英語の紹介を使う。

## 構成

React / TypeScript / Vinext（Vite・Next互換） / Cloudflare Workers / D1（SQLite） / Drizzle migrations。

UIは日本語／英語に対応し、イベントごとにタイムゾーンを固定する。イベントはURLで共有し、イベントを越えた共通ユーザーアカウントは作らない。内部IDはランダム値。ソースコードと実データは分離する。D1、秘密情報、ローカル実行状態はGitへ保存しない。

## 公開版の運用

公開サービスはCloudflare WorkersとD1で稼働している。無料プランを前提とし、ソースコードはこの公開リポジトリで管理する。GitHub上のソースコードと、Cloudflareに保存するイベント・認証情報は別に管理する。

`main`への変更はGitHub Actionsの「Check OpenTonton」で検証する。公開版への反映は「Deploy to Cloudflare (manual)」を`main`ブランチで手動実行する。コミットだけでは本番へ自動デプロイしない。READMEなど説明文だけの変更では、サービスの再デプロイは不要。

デプロイ時は依存監査（High以上で停止）・型チェック・テスト・ビルド・結合テストを行い、D1の未適用マイグレーションを適用してからWorkerを更新する。期限切れデータの清掃は毎時のCron Trigger `0 * * * *`と書込時に実行する。

## 利用上の制限

- 新規作成のリクエストは、同じIPから1分間に10回を目安に制限する。失敗も含め、D1へ到達する前に判定する。
- 作成成功は、同じIPから1時間に20件まで。内部エラーでは消費せず、毎時00分にリセットする。職場・自宅などで同じIPを共有する場合は合算される。
- 作成後の候補日・候補時間の変更は現在未対応。タイトル・説明・受付状態と確定日時は変更できる。
- パスワードを忘れた場合は復旧コードを使う。メールによる再設定は行わない。

API閲覧は同じIPから毎分120回、書込は毎分60回を目安に制限する。さらにCloudflare拠点ごとに閲覧1,000回・書込200回／分の受入制限を設ける。Cloudflare Rate Limitingは拠点ごとの概算制限であり、厳密な全世界共通の上限ではない。作成成功の毎時20件はD1トランザクションで厳密に管理する。これらの対策でも、分散攻撃によるWorkersやD1の無料枠の消費を完全に防げるわけではない。

## 開発

Node.js 24以上、pnpm 11.25.0を使用。

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

ローカルDBのマイグレーション適用（初回・スキーマ更新時）：

```sh
pnpm exec wrangler d1 migrations apply DB --local --config dist/server/wrangler.json --persist-to .wrangler/state
pnpm dev
```

開発用と公開先のデータベースは別。再実行時には未適用のマイグレーションだけ適用する。

```sh
pnpm test:integration
```

結合テストはビルド済みWorkerと隔離した一時D1で実行する。実データに接続しない。作成・認証・権限・候補外拒否・更新競合・受付終了・復旧・期限と連鎖削除に加え、認証競合、DB到達前の制限、防御ヘッダー、SQL／HTML／認証データの注入を確認する。

## 自分のCloudflare環境で運用する場合

以下は、この公開サービスとは別に、自分のアカウントで運用するための初期設定手順。公開サービスの利用者が行う必要はない。独自ドメインなしで、Cloudflareのworkers.dev URLから運用できる。

1. このリポジトリを自分のGitHubアカウントへフォークする。
2. CloudflareのWorkers Freeプランで、`opentonton`というD1データベースを作成する。workers.devのサブドメインも設定する。
3. GitHubリポジトリに`production`というEnvironmentを作る。この名前はデプロイワークフローの`environment: production`に合わせる。
4. Environment secretに`CLOUDFLARE_API_TOKEN`を登録する。Workersのデプロイと対象アカウントのD1操作に必要な範囲に限定し、トークンをソースへ書き込まない。
5. Environment variablesに`CLOUDFLARE_ACCOUNT_ID`と`CLOUDFLARE_D1_DATABASE_ID`を登録する。
6. 運用者として、利用条件・プライバシーに関する説明・問い合わせ窓口を用意する。
7. GitHub Actionsの「Deploy to Cloudflare (manual)」を`main`ブランチで実行する。
8. 自分の公開URLで動作を確認し、CloudflareでCron Trigger `0 * * * *`が設定されていることと、清掃の実行結果を確認する。READMEの公開リンクも自分のURLへ変更する。

生成設定はデプロイ時に指定したD1へ置き換える。アカウントの利用量と無料枠の上限は運用中も確認し、制限に達する場合は負荷や構成を見直す。認証の反復回数を減らすことを運用上の対処にはしない。

## 削除・プライバシー

- DBの外部キー連鎖削除でイベント・参加者・認証情報・セッションを削除する。
- 清掃は1回100イベントずつに制限し、大量失効時はリクエスト時の清掃も併用する。保有上限と清掃遅延を監視すること。
- Cloudflare D1 Freeの復旧用履歴には削除後最大7日残り得る。バックアップから復元するときは公開再開前に期限切れを除去する。
- サーバーのリクエスト本文・パスワード・コード・回答はログへ出力しない。Worker Observabilityは明示的に無効。基盤のセキュリティ処理まで停止することを意味しない。
- 外部アクセス解析、メール送信、外部フォントは使用しない。
- 端末の最近開いたイベント一覧はlocalStorageに最大12件（ID・タイトル・期限のみ）。期限切れは一覧から除外する。認証はCookieに格納し、パスワードや復旧コードはブラウザーへ永続保存しない。

## 認証処理とWorkersの制限

ブラウザーのWeb Cryptoで、パスワードごとのランダム128bitソルトを使いPBKDF2-SHA256を600,000回実行する。登録・参加・復旧では新しいソルトを発行し、ログイン・認証情報変更・削除の確認では `/credentials` から公開KDFパラメーターだけを取得する。パスワード原文は送信しない。送信される導出値はパスワード相当の秘密情報として扱い、HTTPS以外での利用、ログ出力、ブラウザーへの永続保存を禁止する。

サーバーは導出値に別のランダム128bitソルトと用途識別子を加えSHA256で再ハッシュする。DBには方式・反復回数・二つのソルト・再ハッシュ後の値を保存する。DB内の値をそのまま送ってもログインできず、パスワード推測には各パスワード固有の600,000回の計算が必要になる。Worker内ではPBKDF2を実行しない。サーバーが悪意あるクライアントの実際の反復回数を証明できる方式ではないため、公式画面での入力長検証に加え、サーバーは導出値の方式・長さ・形式を検証する。

認証変更・復旧時はランダムな認証世代を更新し、セッション発行は最新世代との一致をDBで確認する。復旧コードの消費、認証変更、旧セッションの削除、新セッションの発行を同じトランザクションで扱い、同時実行された古い認証処理を拒否する。既存DBには追加マイグレーションで認証世代の列とセッション検索用インデックスを加える。

旧形式の保存済みハッシュは削除せず、復旧コードによる再設定で新形式に移行する。旧画面からパスワード原文が送信された場合は、画面の再読み込みを案内する。結合テストではWorker内のPBKDF2を意図的に無効化し、ブラウザー用送信処理を通した作成・ログイン・変更・復旧・削除を確認する。

IP原文は保存せず、回数制限に必要な時間窓ごとのハッシュ識別子だけを期限付きで保持する。

## 入力値とブラウザーの保護

タイトル・説明・ニックネームはSQLのパラメーターとして渡し、画面ではReactの文字列として描画する。ユーザー入力をHTML、JavaScript、SQLへ連結しない。パスワード原文はブラウザーで処理し、APIは方式・ソルト・導出値の形式を検証する。CSV出力は引用符のエスケープに加え、空白や全角記号を含む数式開始文字への対策を行う。JSON本文は読み取り中に64KBで打ち切る。

HTMLとAPIのレスポンスにはCSP、フレーム埋め込み禁止、`no-referrer`、`nosniff`などを付ける。CSPのスクリプトnonceはリクエストごとに生成し、呼出元から渡された値は使用しない。HTMLは`no-store`とし、静的アセットの共通ヘッダーは`public/_headers`で設定する。
